# 澄清策略

VibeGuard 的澄清不是为了把流程变复杂，而是为了避免一开工就走错方向。

## 目录

- 什么时候必须问
- 什么时候可以带假设推进
- 不应该问什么
- 问题优先级
- 常用提问模板

## 什么时候必须问

出现以下情况时，先问用户，不要直接生成最终 brief：

1. **目标不清**：无法用一句话说清楚这次到底要完成什么。
2. **成功标准不清**：不知道什么结果出现才算完成。
3. **输入输出不清**：不知道用户输入什么、系统输出什么、数据从哪里来。
4. **范围边界不清**：不知道这次做哪些、不做哪些。
5. **改动权限不清**：不知道 AI 可以改哪些文件、模块、接口、数据结构。
6. **兼容性要求不清**：可能影响旧用户、旧接口、旧数据、现有流程。
7. **多种实现路径差异很大**：比如“导入数据”可能是 CSV、Excel、API、手动粘贴。
8. **涉及高风险操作**：支付、权限、登录、数据迁移、删除、批量修改、外部 API、隐私数据。

## 什么时候可以带假设推进

如果不确定项不会改变整体方向，可以写明假设后继续：

- 文案细节；
- 局部 UI 排版；
- 非核心命名；
- 可从现有代码风格推断的小实现细节；
- 第一版可以先用简单实现替代复杂方案；
- 用户已经表达“先给我一版，我再改”。

输出时写：

```markdown
可以先按以下假设推进：
- ...

如果这些假设不对，后续需要局部调整。
```

## 不应该问什么

不要机械追问：

- 用户已经明确说过的信息；
- 不影响第一版实现的问题；
- 可以通过读代码/看现有页面快速确认的问题；
- 只是为了填满模板的问题；
- 太早问商业化、增长、技术栈大改等超出当前任务的问题。

## 问题优先级

最多先问 3-5 个关键问题。优先问会改变实现方向的问题。

### P0：不问就不能开工

- 一句话目标是什么？
- 什么结果算完成？
- 这次不做什么？
- 哪些地方不能改？
- 数据/接口/权限来源是什么？

### P1：不问容易返工

- 第一版做到什么程度？
- 是否需要兼容旧数据/旧流程？
- 有没有必须遵守的 UI/交互/代码风格？
- 是否已有相关模块或参考页面？

### P2：可以后置

- 文案语气；
- 细节命名；
- 样式微调；
- 后续版本扩展；
- 非核心配置项。

## 常用提问模板

### 模糊 idea

```text
我先确认几个会影响实现方向的问题，不展开成大需求评审：
1. 这个功能主要给谁用？
2. 第一版只需要完成哪一个核心动作？
3. 这次明确不做什么？
4. 什么结果出现时，你会觉得“可以先用了”？
```

### 功能开发

```text
这件事基本可以整理成开发 brief。我只需要补两个边界：
1. AI 可以改哪些页面/模块？
2. 哪些现有行为不能被影响？
```

### 修 bug

```text
修 bug 前先补最关键的信息，避免只把报错压下去：
1. 预期行为是什么？
2. 实际行为是什么？
3. 复现步骤是什么？
4. 最近改过登录/路由/数据/接口相关逻辑吗？
```

### 重构

```text
重构最重要的是别改坏外部行为。我先确认：
1. 这次重构的目标是可读性、性能、解耦，还是迁移？
2. 哪些外部行为必须保持不变？
3. 允许改哪些模块？
4. 怎么验证重构没有改坏功能？
```

## 输出建议

如果需要提问，最后也可以给一个“当前已知 brief 草稿”，让用户感觉任务在推进：

```markdown
我先按当前信息整理一版草稿，缺的地方标出来：

## 已知
- ...

## 需要你确认
- ...
```
