# AI Coding 常见失败模式

这个文件用于识别 AI Coding 容易出问题的地方，并把风险转成 brief 里的边界、假设、验收标准和停止条件。

## 目录

- 需求理解类
- 范围控制类
- 上下文类
- Bugfix 类
- 重构类
- 代码结构类
- 验收类
- 如何转成 brief

## 需求理解类

### 1. 表面需求清楚，真实目标不清

表现：用户说“加个按钮”，但真正想完成的是某个业务流程。

风险：AI 只做 UI，不解决真实问题；或者按自己的理解补业务逻辑。

写进 brief：

- 目标要写业务结果，不只写 UI 动作；
- 已知上下文里写清按钮触发什么流程；
- 未知项里标出业务规则缺失。

### 2. 模糊词不可验收

表现：优化一下、更高级、更智能、更好看、更丝滑。

风险：AI 随机发挥，改很多无关内容。

写进 brief：

- 把模糊词改成可检查标准；
- 例如“更好看”改成“保持现有品牌色，提升首屏标题层级，移动端不破版”。

### 3. 多种实现路径差异很大

表现：导入、同步、推荐、权限、自动化、报表等词没有说明具体机制。

风险：AI 选错方向，后续返工很大。

写进 brief：

- 触发 NO-GO 或先问；
- 至少确认输入、输出、数据来源、执行时机。

## 范围控制类

### 4. 没有非目标

表现：只写“要做什么”，没写“不做什么”。

风险：AI 把小功能扩展成完整系统。

写进 brief：

- 增加“这次不做”；
- 增加“禁止改动”；
- 增加“不要重构/不要换技术栈/不要新增后台配置”等明确限制。

### 5. 改动权限不清

表现：不知道哪些文件、模块、接口、数据结构能改。

风险：AI 改到支付、登录、公共组件、数据模型等高风险区域。

写进 brief：

- 写 Allowed changes；
- 写 Must not change；
- 如果用户不知道，标为需要确认。

### 6. 小需求被升级成大工程

表现：加一个 FAQ，AI 顺手重构设计系统；修一个 bug，AI 改了路由体系。

风险：改动不可控，Review 成本高。

写进 brief：

- 加 Stop condition：如果需要跨模块重构，先停下来问；
- 加 Acceptance：只检查当前目标，不引入额外功能。

## 上下文类

### 7. 长对话上下文污染

表现：旧方案、废弃想法、当前任务混在一起。

风险：AI 采纳过期信息。

写进 brief：

- 增加 Current-Task Brief；
- 把事实、假设、未知项分开；
- 明确“以这份 brief 为准”。

### 8. 把假设当事实

表现：AI 默认了技术栈、文件位置、业务规则、接口行为。

风险：实现看似合理，但不符合真实项目。

写进 brief：

- 明确 Known context；
- 明确 Assumptions；
- 关键假设不成立时必须停下来问。

## Bugfix 类

### 9. 只让报错消失

表现：报错没了，但根因没解决，后面又冒出别的问题。

风险：补丁堆叠，代码越来越难维护。

写进 brief：

- 必须写预期行为、实际行为、复现步骤；
- 要求先说明可能根因，再改代码；
- 连续两次失败后停止打补丁。

### 10. 没有复现步骤

表现：用户只说“有问题”“不对”“坏了”。

风险：AI 只能猜。

写进 brief：

- 标记复现步骤未知；
- 优先追问；
- 如果先推进，只允许做定位和日志/检查建议，不直接大改。

## 重构类

### 11. 重构变重写

表现：用户说“整理一下”，AI 直接换架构、换库、改公共接口。

风险：行为变化、兼容性破坏、测试失效。

写进 brief：

- 明确保持不变的外部行为；
- 禁止换技术栈/重写模块，除非用户明确要求；
- 验收必须包含原行为检查。

### 12. 没有验证方式

表现：改完不知道是否真的保持一致。

风险：代码变整洁了，但功能坏了。

写进 brief：

- 如果有测试，要求测试通过；
- 如果没有测试，写人工验证步骤；
- 无法验证时触发 Stop condition。

## 代码结构类

### 13. 状态归属不清

表现：AI 为了让当前功能跑通，新增全局变量、全局 store、模块级缓存或到处传临时 flag。

风险：旧值、脏数据、用户切换、重复打开页面或并发请求时出现莫名其妙的 bug。

写进 brief：

- 明确新增状态属于组件、页面、store、context 还是后端；
- 默认禁止新增可变全局变量或模块级业务缓存；
- 如果必须新增全局状态，先说明局部状态为什么不够。

### 14. 前后端边界混乱

表现：权限只在前端隐藏按钮，错误码靠前端猜字符串，数据转换散在多个组件里。

风险：安全兜底不足，接口改动后多处一起坏，业务规则重复且不一致。

写进 brief：

- 明确哪些校验必须后端兜底；
- 明确 API 字段、类型、空值、错误码是否允许改；
- 接口契约不清时触发 Stop condition。

### 15. 命名和调用关系混乱

表现：函数名很泛，`handleSubmit` 里塞保存、校验、跳转、埋点、状态重置；新增一个和已有函数差不多但名字不同的实现。

风险：后续 AI 和人都根据名字误判职责，越改越难定位。

写进 brief：

- 沿用现有命名风格；
- 不新增职责重复但名字不同的函数/组件/API；
- 如果一个函数承担多件事，先拆职责或说明为什么保留。

### 16. 跨层访问内部实现

表现：UI 组件直接读底层数据结构，页面绕过 API 封装调用内部函数，公共组件依赖业务模块。

风险：模块之间互相知道内部细节，一处改动牵连多处。

写进 brief：

- 写清模块边界和允许调用的公开接口；
- 禁止反向依赖和跨层访问内部状态；
- 如果需要改变公共函数/组件行为，先问用户。

## 验收类

### 17. 没有完成标准

表现：AI 不知道何时停，越做越多。

风险：范围扩张，产物不可控。

写进 brief：

- Done when 必须具体；
- Verification 必须可执行；
- Stop and ask if 必须写清楚。

### 18. 只写“测试通过”但不知道测什么

表现：项目没有测试，或者测试不覆盖当前行为。

风险：虚假安全感。

写进 brief：

- 写具体手动验证步骤；
- 写样例输入输出；
- 写关键页面/流程检查。

## 如何转成 brief

发现失败模式后，不要只提醒用户“这里有风险”。要把它转成具体字段：

| 发现的问题 | 转成 brief 字段 |
|---|---|
| 目标模糊 | 一句话目标 + 需要确认的问题 |
| 范围膨胀 | 这次不做 + 禁止改动 |
| 假设过多 | 关键假设 + 未知项 |
| Bug 没复现 | 复现步骤未知 + 停止条件 |
| 重构风险 | 保持不变的行为 + 验收方式 |
| 状态归属不清 | 代码结构约束：状态归属 + 全局变量限制 |
| 前后端边界混乱 | 代码结构约束：前后端/API 边界 + Stop condition |
| 命名和调用关系混乱 | 代码结构约束：命名与调用关系 + 可维护性检查 |
| 验收不清 | Done when + Verification |
| 长上下文混乱 | Current-Task Brief + 以 brief 为准 |

输出时要让用户拿到可执行结果，不要停留在分析。
