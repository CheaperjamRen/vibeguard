# 开工闸门：GO / GO WITH ASSUMPTIONS / NO-GO

这个文件用于判断当前任务能不能交给 AI Coding 工具开始写代码。

目标不是制造流程，而是避免在目标、边界、验收都不清楚时直接开工。

## 目录

- 判断结果
- GO 标准
- GO WITH ASSUMPTIONS 标准
- NO-GO 标准
- 风险等级
- 输出模板

## 判断结果

### GO

可以开工。需求目标、范围、关键上下文、验收方式基本清楚。

### GO WITH ASSUMPTIONS

可以先开工，但必须把假设写进 brief。适合不确定项较少、且不会改变整体方向的任务。

### NO-GO

不建议现在开工。不是流程问题，而是当前信息不足以判断“做完算不算对”，或者风险太高。

## GO 标准

满足以下条件时，可以给 GO：

- 一句话目标明确；
- 第一版范围基本清楚；
- 非目标明确；
- 允许改动和禁止改动基本清楚；
- 关键输入输出明确；
- 验收标准可检查；
- 有基本验证方式；
- 风险可控，即使假设不成立也不会造成大返工。

输出示例：

```markdown
判断：GO

这份需求已经可以交给 AI Coding 工具开工。建议直接使用下面的 Current-Task Brief。
```

## GO WITH ASSUMPTIONS 标准

满足以下情况时，给 GO WITH ASSUMPTIONS：

- 目标清楚，但有少量细节未知；
- 未知项不会改变整体实现方向；
- 可以通过明确假设降低误解；
- 用户更希望先推进，而不是继续讨论；
- 验收方式至少有一个可执行版本。

输出示例：

```markdown
判断：GO WITH ASSUMPTIONS

可以先开工，但建议带着这几个假设推进：
- 默认不改变现有接口返回结构；
- 默认只做第一版，不加入后台配置；
- 默认沿用现有页面风格。

如果这些假设不成立，后续需要局部调整。
```

## NO-GO 标准

出现以下任一情况，给 NO-GO：

- 目标含糊，无法判断最终结果；
- “优化一下”“更高级”“更智能”这类描述没有可检查标准；
- 关键数据源、接口、权限、输入输出未知；
- 多个实现方向差异很大，选错会大量返工；
- 涉及支付、登录、权限、隐私、删除、数据迁移等高风险操作，但没有边界和验证方式；
- 用户要求和现有约束冲突；
- 不知道哪些文件/模块能改，哪些不能改；
- 修 bug 没有预期行为、实际行为或复现步骤；
- 重构没有说明外部行为如何保持不变。

输出示例：

```markdown
判断：NO-GO

我不建议现在直接交给 AI 写代码。主要问题不是代码难，而是现在还不知道“做完算不算对”。

需要先确认：
1. ...
2. ...
3. ...
```

## 风险等级

### 低风险

- 文案；
- 小样式；
- 单页面小改动；
- 可人工快速验证。

处理方式：Tiny Brief 即可。

### 中风险

- 普通功能；
- 一般 bugfix；
- 小范围重构；
- 涉及多个文件但边界清楚。

处理方式：Standard Brief + 验收标准。

### 高风险

- 登录、支付、权限；
- 数据迁移、删除、批量修改；
- 跨模块架构调整；
- 公共 API 或数据结构变更；
- 无法本地验证；
- 用户描述模糊但期望一次做对。

处理方式：Spec Brief + Gate 判断 + Stop Contract。

```markdown
- ...
```

## 注意

不要把 NO-GO 写成拒绝用户。它只是提醒：现在直接开工大概率会改偏。给出最少需要补充的信息，帮助用户继续推进。
