# 代码结构护栏

这个文件用于在 AI Coding 前或重构前，补上代码结构层面的约束。

它解决的不是“代码要优雅”这种空话，而是这些具体问题：代码耦合越来越重、前后端边界混乱、函数名和调用关系对不上、全局变量/全局状态到处传、修一个小 bug 引出另一个 bug。

## 什么时候使用

当用户提到以下情况时使用：

- 担心代码后面不好维护；
- 担心 AI 改出一堆耦合；
- 前端、后端、接口、数据处理边界说不清；
- 函数名、变量名、组件名、接口名混乱；
- AI 总是定义全局变量、全局状态或临时缓存；
- 修一个 bug 之后另一个地方坏了；
- 想重构，但不知道该怎么限制范围；
- 需求涉及前后端联调、API、状态管理、数据流；
- 用户说“代码规范”“开发规范”“架构边界”“可维护性”。

如果只是改文案、改颜色、改一个固定样式，不要强行使用完整清单。最多补一句“不要改状态和数据流”。

## 为什么 AI 容易写出这类问题

### 1. AI 会优先补齐局部代码，不一定理解长期结构

AI 很擅长根据当前文件附近的代码补出“看起来能跑”的实现。但如果 brief 没有写清模块边界，它可能直接跨层调用、跨文件读状态、绕过已有封装。

短期看：功能出来了。后期看：调用链变乱，下一次改动更容易误伤。

### 2. AI 不知道某个状态应该归谁管

很多 bug 本质上不是语法问题，而是状态归属不清：

- 表单值应该归组件内部管，还是归页面级 store 管；
- 登录态应该来自后端 session/token，还是前端本地缓存；
- 某个 loading/error 状态应该属于请求函数、组件，还是全局状态；
- 某个配置应该来自服务端、环境变量，还是写死在前端。

如果不写清楚，AI 容易用最方便的方式解决：加一个全局变量、全局 store、模块级缓存或临时 flag。

### 3. 前后端边界不清时，AI 会把逻辑放到“它当前最容易改的地方”

比如：

- 权限判断本来应该后端兜底，AI 只在前端隐藏按钮；
- 数据格式本来应该在 API 层统一，AI 在每个组件里各自转换；
- 错误码本来应该服务端返回稳定枚举，AI 在前端用字符串匹配；
- 业务规则本来应该在领域逻辑里，AI 写进 UI 事件处理函数。

这类代码一开始能用，后面会很难改，因为规则散在不同地方。

### 4. 命名不一致会让 AI 后续继续误解

AI 会根据名字推断用途。函数叫 `handleSubmit`，但里面其实做了保存、校验、跳转、埋点、状态重置，后面再让 AI 改“提交逻辑”，它可能不知道该改哪一段。

命名混乱会造成两个问题：

- 人看不懂调用关系；
- AI 下一轮会根据错误名字继续生成错误代码。

### 5. 全局变量会制造隐形依赖

全局变量、模块级可变变量、到处都能改的 singleton，最大的问题不是“写法不好看”，而是它隐藏了输入输出。

一个函数表面上只接收两个参数，实际还依赖全局状态。下次测试、并发请求、切换用户、重复打开页面时，就可能出现莫名其妙的旧值、脏数据或顺序问题。

## 开工前先确认的结构问题

在生成开发 brief 前，先确认这些信息。缺失时写“未知”或“需要确认”，不要替用户编。

1. **影响层级**：这次只改 UI，还是要改 API、数据结构、状态管理、后端逻辑？
2. **数据来源**：页面/函数需要的数据从哪里来？API、props、store、本地缓存，还是用户输入？
3. **状态归属**：新增状态应该放在哪里？组件内部、页面级、全局 store、后端？
4. **副作用位置**：请求、写缓存、埋点、跳转、toast、日志应该由谁触发？
5. **接口契约**：前后端字段名、类型、错误码、空值、默认值是否已经明确？
6. **命名约定**：现有项目怎么命名组件、函数、hook、API 方法、store action？
7. **禁止区域**：哪些公共组件、公共函数、数据模型、全局状态不能改？
8. **验证方式**：结构改动如何验证没有破坏旧路径？

## 六类代码结构护栏

### 1. 模块边界

要写清：

- 这次允许改哪些模块；
- 哪些模块只能调用公开接口，不能读内部实现；
- 不要为了方便从 UI 层直接访问底层数据结构；
- 不要把业务规则写散到多个页面或组件里。

写进 brief 的方式：

```text
代码结构约束：
- 只允许改 [模块/文件]。
- [A 模块] 只能通过 [公开函数/API] 调用 [B 模块]，不要读取 B 的内部状态。
- 不要把业务规则写进 UI 组件；如果必须新增规则，先说明应该放在哪一层。
```

### 2. 前后端契约

要写清：

- 哪些校验必须后端兜底；
- 前端只负责展示/交互，还是也负责轻量校验；
- API 字段名、类型、空值、错误码是否固定；
- 不能只靠前端隐藏按钮实现权限。

写进 brief 的方式：

```text
前后端边界：
- 前端可以做交互校验，但权限/数据合法性必须以后端结果为准。
- 不要在前端猜测后端错误文案；按现有 error code / response 字段处理。
- 如果需要新增或修改 API 字段，先停下来确认接口契约。
```

### 3. 状态归属

要写清：

- 新增状态属于组件、页面、全局 store 还是后端；
- 不要因为跨组件传值麻烦就直接放全局；
- loading、error、selected item、draft data 这些状态各自归谁管；
- 是否需要清理状态，避免旧值污染下一次操作。

写进 brief 的方式：

```text
状态归属：
- 本次新增状态优先保持在 [组件/页面] 内，不新增全局状态。
- 只有多个独立页面都需要共享时，才考虑 store；如果要新增 store，先说明原因。
- 请求完成、弹窗关闭、用户切换或页面离开时，需要清理临时状态。
```

### 4. 全局变量和隐形依赖

默认规则：

- 不新增可变全局变量；
- 不用模块级变量保存用户相关数据、请求结果或临时 UI 状态；
- 不让函数偷偷依赖外部可变状态；
- 需要共享数据时，优先使用现有 store、context、参数传递或服务端状态。

写进 brief 的方式：

```text
全局变量限制：
- 不新增可变全局变量或模块级缓存来保存业务状态。
- 函数依赖的数据要通过参数、props、context/store 或明确的数据源传入。
- 如果认为必须用全局状态，先说明为什么局部状态不够。
```

### 5. 命名和调用关系

要写清：

- 函数名要描述真实动作，不要用万能名；
- 组件名、hook 名、API 方法名要和现有项目风格一致；
- 不要新增和已有概念相似但名字不同的函数；
- 修改函数职责时，同步检查调用方是否仍然符合名字含义。

写进 brief 的方式：

```text
命名约束：
- 新函数/组件/API 方法沿用现有命名风格。
- 不新增与现有函数职责重复但名字不同的实现。
- 如果一个函数需要同时做多件事，先拆清职责，不要塞进 handleXXX 里。
```

### 6. 可维护性最小检查

不要求每次都做大型架构设计，只做几个最小检查：

- 新增逻辑有没有唯一归属；
- 有没有把业务规则复制到多个地方；
- 有没有引入反向依赖；
- 有没有把临时状态做成全局状态；
- 有没有用名字掩盖复杂职责；
- 有没有为了当前 bug 加一个以后没人敢删的补丁。

## 如何写进 brief

如果任务涉及代码结构风险，在普通 VibeGuard Brief 中增加这一段：

```markdown
## 代码结构约束

模块边界：
- ...

前后端/API 边界：
- ...

状态归属：
- ...

全局变量限制：
- ...

命名与调用关系：
- ...

可维护性检查：
- ...
```

如果信息不足，不要补得太满，可以写：

```text
代码结构约束：
- 状态归属未知：需要先确认是否已有 store/context。
- API 契约未知：不要擅自修改字段名或错误码。
- 命名约定未知：先沿用相邻文件的命名，不新增平行概念。
```

## 质量检查清单

生成 brief 前，检查：

- 是否写清楚哪些层可以改，哪些层不能改；
- 是否写清楚新增状态归哪里；
- 是否禁止了不必要的全局变量/全局状态；
- 是否说明前端不能替代后端权限/数据校验；
- 是否要求沿用现有命名和调用风格；
- 是否禁止重复造一个相似函数/组件/API；
- 是否给了结构层面的停止条件；
- 是否有验证旧路径没有坏的步骤。

## 示例表达

推荐：

```text
这次最大风险不是功能写不出来，而是状态放错地方。先确认这个状态应该归组件、页面还是全局 store。
```

```text
不要为了让当前页面跑通，就在前端写死后端字段或错误文案。接口契约不清楚时先停下来问。
```

```text
这里不建议新增全局变量。这个值如果只服务当前弹窗，就留在弹窗或页面状态里。
```

```text
如果新增函数和已有函数只有名字不同、职责差不多，优先复用或调整现有函数，不要再造一个平行版本。
```

避免：

```text
请进行架构治理并优化代码工程质量。
```

```text
请确保前后端链路高内聚低耦合。
```

```text
建立统一状态管理底座。
```

这些话太空，AI 不知道具体该做什么。要写成它能执行和停下来的约束。
